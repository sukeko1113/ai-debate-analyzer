# 0. この文書の位置づけ

*技術仕様ではなく、初めて聞く人にも「何を作るのか・なぜ必要か」が伝わる全体像を示す。*

基本設計書 v08 は、データ構造、画面、API、音声処理、検証、権限などを実装できる粒度まで具体化した「システム設計」である。本書はそこから技術実装をいったん外し、プロジェクトの目的・体験・価値・利用場面を説明する「コンセプト設計書」として再構成した。

| What | Why | For whom |
|---|---|---|
| 英語ディベートの試合を「後から検証できる議論の地図」に変える | 勝敗だけでは分からない「どこで議論が崩れ、何が最後に残ったか」を説明する | ジャッジ、指導者、選手、初心者、観客、大会運営・研究者 |

本書では Next.js、データベース、API、クラウド構成などの技術スタックは扱わない。それらは v08 基本設計書の役割とする。

# 1. このアプリを一言でいうと

> **30秒で説明すると**
> 「英語ディベートの録音・録画を入れると、AI が発言を整理してフローシートと判定材料を作り、人間ジャッジが確認・修正する。最終的には、どの議論がどこで攻撃され、どこまで守られ、何が勝敗を決めたかを、元の発言へ戻れる形で説明できるアプリ」です。

ポイントは「自動ジャッジ」ではない。AI は候補を作り、判断の根拠を整理する。最終的な判定は人間が行う。

| よくある誤解 | 本プロジェクトの考え方 |
|---|---|
| AI が試合を採点して勝者を決める | AI は候補を提示し、人間ジャッジが確定する |
| 文字起こしアプリである | 文字起こしは入口。中心は「議論のつながり」と「判定過程」の可視化 |
| 独自の100点満点で議論を採点する | HEnDA の Probability / Value / Strength など公式表現を正本にする |
| きれいな要約を作る | 誰が・いつ・何を・どの議論に対して言ったかを追跡できる記録を作る |
| ジャッジの判定は1試合につき1つである | 複数のジャッジが同じ試合を見て割れることがある。その割れ方こそ記録する（§14） |

# 2. そもそも HEnDA 型ディベートで何が起きているか

初めて見る人には、英語ディベートは「英語で意見を言い合う競技」に見える。しかし実際には、主張を作り、相手の証明を攻撃し、自分の議論を守り、最後に両者を比較する構造化された競技である。

| 段階 | 何をするか |
|---|---|
| Constructive / 立論 | 自分たちの Advantage / Disadvantage を、現状・因果・重要性・根拠で組み立てる |
| Attack / 反論 | 相手の議論の「どこが弱いか」を特定し、成立を崩す |
| Defense / 再構築 | Attack に答え、自分の議論を立て直す。後出しの新規議論は避ける |
| Summary / 総括 | 試合全体を整理し、残った Advantage と Disadvantage を比較して勝ち筋を示す |

質疑（Questions）は各段階の間に入り、相手の立論や Attack の確認・検証に使われる。HEnDA の試合は、こうした役割が定められた順番で進行する。

なお、この12ステージの前には開会と自己紹介がある。計時の対象ではなく、判定材料でもない。しかし後述するとおり（§4）、この区間は設計上とても重要である。

# 3. なぜ今のままでは「なぜ勝ったか」が分かりにくいのか

ディベートの勝敗は、最後の Summary だけを聞いても理解しにくい。重要なのは、最初の立論が途中でどう変化したかである。ところが、その変化は通常ジャッジのフロー用紙と頭の中にしか残らない。

| 利用者 | 今起きている困りごと |
|---|---|
| ジャッジ | 短時間で大量の発言を聞きながら、論点の対応関係と判定理由を同時に追う必要がある |
| 指導者 | 「負けた理由」を選手へ具体的に説明しようとしても、発言箇所と論点を探し直す手間が大きい |
| 高校生・初心者 | Attack が「何を壊したのか」、Defense で「何が戻ったのか」が見えにくい |
| 観客 | 英語を全部聞き取れても、どの議論が優勢なのかを追うのが難しい |
| 大会運営・研究 | 同じ試合でもジャッジごとの判断差を比較する共通データが残りにくい |

> **解決したい本質**
> 勝敗の「結果」を記録するだけでなく、判定に至るまでの「議論の変化」を記録する。これが本アプリの中心課題である。

# 4. 実試合1本で確かめたこと（v06で新設）

v05までのコンセプトは、頭の中で想定した「きれいな試合」を前提にしていた。実際の決勝戦を1本読むと、想定と現実が一致した部分と、そもそも想定していなかった部分が、はっきり分かれた。

## 4.1 想定どおりだったこと

- **座席は自動で決まる。**HEnDA では各スピーチの担当が大会ルールで決まっている。実試合でも、8名全員の担当が①〜⑫のすべてで矛盾なく決まった。①で立論した人が②で質問に答え、④で質問した人が⑪で総括する、という対応がぴったり合った。「誰が話しているか」を声で当てる必要はない。
- **議論は4つの部品に分けられる。**「進行がん患者の約10%は激痛を制御できない」（現状）、「安楽死でしか救えない領域がある」（因果）、「耐え難い苦痛からの解放」（重要性）、「緩和ケア病床は3,399床しかない」（根拠）。否定側の攻撃は、この4つのどれに当たったかで整理できた。
- **勝敗を分けたのは、残った論点の比較だった。**判定理由も講評も、最後は「肯定側に残った利益」と「否定側に残った不利益」を並べて比べている。アプリが支援すべきはここである。

## 4.2 想定していなかったこと

| 現実 | v05のコンセプトでの扱い | v06での考え方 |
|---|---|---|
| 判定は5人の審判が下し、結果は4対1だった | 判定は1つという前提 | 判定はジャッジ1人につき1つ。割れたら割れたまま残す（§14） |
| 10分ぶん・スピーチ2つぶんの記録が丸ごと失われていた | 「聞き取れなかった」しか無い | 「記録が無い」を別のものとして扱う（§13） |
| 座席と氏名の対応は、開会の自己紹介にしか無かった | 12ステージだけを扱う | 自己紹介ラウンドを保持する。ただし判定材料にはしない |
| 審査委員長は表現力と共感を勝因として語り、客観的な判定理由はそれを論証の言葉に置き換えていた | Communication は勝敗と別枠、とだけ書いてあった | どちらも残す。分かれたことが見えるようにする（§12） |
| 「そのリスクはほぼ無視できる」で議論が止まっていた | Strength に None を置ける、としか書いていない | 「ゼロにした理由」を書く欄を作る（§10） |
| 自動の話者分離は、同じ人を別人に分け、別人を同じ人にまとめていた | 話者分離は「不要」 | 「不要」ではなく「使わない」。誤ったラベルは人の判断を歪める |

> **この節が伝えたいこと**
> 想定していなかったことのうち、半分以上は「記録できない」ではなく「間違って記録してしまう」種類だった。空欄は目立つので誰かが気づく。しかし、誤って埋まった欄には誰も気づかない。
> 記録が無いだけの区間を「相手の主張に応答しなかった」と記録する。5人のうち1人だけ違う判断をしたことを消す。表現がうまかったという評価を、議論が強かったという評価として残す。どれも画面上はきれいに埋まって見える。
> だから本アプリは、埋まっていることではなく、正しく埋まっていることを目標にする。

# 5. 中核コンセプト：ジャッジの思考過程を見える化する
人間ジャッジが行っている仕事を、次の10段階として可視化する。v07では、単に「最後に残った論点を見る」だけでなく、評価理由と採用可否を分け、Voting Issue を決めた根拠まで追跡する。

| # | 段階 |
|---|---|
| 1 | 立論を Observation / Link / Impact に分解する |
| 2 | Evidence / Warrant / Relevance / Burden を確認し、Probability の根拠を整理する |
| 3 | Attack がどのノードを狙ったかを見る |
| 4 | Defense でどこまで戻ったかを見る |
| 5 | Drop・Concession・質疑での確認をイベントとして残す |
| 6 | Summary まで生き残った論点と Impact を比較する |
| 7 | New Argument / Late Repair を採用可否ルールで除外する |
| 8 | Probability × Value = Strength の形で Judge Sheet 候補を作る |
| 9 | Voting Issue を survival と clash leverage の両面から候補化する |
| 10 | AIで確定できない条件なら REVIEW_REQUIRED として人間確認へ止める |

> **v07の追加原則**
> AIに「必ず答えを出させる」ことを品質とは考えない。判断材料が欠けている、Value turn の扱いで勝敗が変わる、Voting Issue の候補が競合する、といった場合に止まれることも、判定支援の精度である。
# 6. 1試合が「見える議論」に変わるまで

ユーザー体験は、技術の詳細ではなく次の6段階で理解できる。

| 段階 | 何をするか | 利用者から見える価値 |
|---|---|---|
| STEP 1 | 試合を取り込む | 録音・録画を読み込み、試合の各ステージを確認する。記録が欠けている範囲があれば、この時点で分かる |
| STEP 2 | 誰がどの席かを決める | 開会の自己紹介と担当表を突き合わせ、A1〜N4 を確定する。氏名は後で消せる形で持つ |
| STEP 3 | 発言を確認する | AI の文字起こしを人が音声へ戻りながら確認する。聞き取れなかった箇所も区別する |
| STEP 4 | 議論をつなぐ | 立論・Evidence・Attack・Defense・Summary の対応関係を Flow として整理する |
| STEP 5 | 判定材料を整理する | AD1/AD2/DA1/DA2 の Probability・Value・Strength、New Argument、Voting Issue の候補を整理する |
| STEP 6 | 「なぜ」を説明する | どの Attack が効き、Defense で何が戻り、Summary で何が決定的だったかを時刻付きで説明する |

STEP 2 はv06で独立させた。実試合で、座席と氏名の結び付けが試合全体の入口になっていたためである。ここを飛ばすと、以降のすべての画面が「Speaker 3」のような意味のないラベルで動くことになる。

> **重要な設計原則**
> AI が勝手に「確認済み」「確定」とすることはない。AI は提案、人間は確認・確定。この線引きが、判定支援ツールとしての信頼性を支える。

# 7. 議論を3つのノード＋Support Qualityに分けると、Attackの意味が見える
v06では Present / Effect / Importance / Evidence-Warrant の4部品として説明していた。v07では HEnDA Judge Sheet の Probability と二重評価しないよう、**3つの論証ノード＋Support Quality** に整理する。

| 内部分析 | 何を表すか | 典型的な Attack |
|---|---|---|
| A. Observation | 現状・前提。ADなら「現状に問題がある」、DAなら「現状では悪影響が起きていない」 | Not necessary / Not unique |
| B. Link 1..n | Planから結果へつながる因果、Effect、Solvency、Process | No effect / Alternative solves / Not solvent |
| C. Impact | 結果がどれほど重要・重大か。規模・期間・不可逆性など | Not important / Value turn |
| Support Quality | Evidence、Warrant、Relevance、Burden。A/B/Cがなぜ成立すると評価されるかの説明 | 出典が弱い、論理飛躍、関連性が低い、立証不足 |

Support Quality は独立した得点として掛け算しない。Judge Sheet の Probability 自体が「事実と証拠によって構築・防御されたか」を見るためである。Evidence / Warrant を別係数にすると、同じ証拠の強さを二重に評価してしまう。

この分解により、「AD1 は崩れた」ではなく、「AD1 の Link2 が NO_EFFECT で攻撃され、Defense で部分回復した。Evidence 自体は残ったが、因果の weakest link が低下したため Probability が Lo 寄りになった」のように説明できる。

> **Evidenceが聞き取れない場合**
> 書き起こしの失敗を論証の弱さに転嫁しない。出典が本当に弱いのか、音声・記録の問題で確認できないのかを分け、後者は UNVERIFIABLE として人間確認へ送る。
# 8. Debate Evolution：議論の変化を時系列で追う

本アプリでは、各 AD/DA が試合中にどう変化したかを「議論の履歴」として見せる。以下は概念例である。

| 時点 | 出来事 | AD1 の状態 |
|---|---|---|
| Constructive | AD1 を A=Observation / B=Link / C=Impact に分解し、Evidence・Warrant を Support Quality として記録 | 議論が成立 |
| NEG Attack | Effect に「既存の手段で足りる」の Attack | 因果が大きく弱化 |
| AFF Defense | 代替手段の適用限界を示す | 一部回復 |
| AFF Summary | AD1 と DA1 を規模・確率・期間で比較 | 比較優位を主張 |
| Judge | 残存した Effect と Importance を確認 | Strong 寄りの候補 |

> **この表示で分かること**
> 「どこで差がついたか」「どの反論が効いたか」「守り切れなかったのはどこか」を、試合の時系列に沿って説明できる。初心者にとっては、フローシートの読み方そのものが学習教材になる。
> この履歴には「AI がそう推定した」と「人がそう確定した」が別の欄として残る。AI の推定を人が上書きするのではなく、両方を並べて残すので、後から見たときにどちらの判断だったかが分かる。人が効果を入力するかどうかは任意で、入力しなくても判定は成立する。

# 9. 4つの衝突点として読む（v06で新設）

Debate Evolution は「いつ何が起きたか」を時間順に並べる。しかし判定理由を書くときに人が実際に行うのは、別の整理である。論点ごとに断面を取り、「この争点は結局どうなったか」を見る。

実試合の分析資料も、試合全体を4つの主要な衝突点（Clash Point）として整理していた。

| 衝突点 | 肯定側の主張 | 否定側の反論 | 衝突の結果 |
|---|---|---|---|
| 肉体的苦痛の救済 | 緩和ケアでは救えない患者が確実にいる | 鎮静で8〜9割は緩和できる／せん妄で同意できない | 適用期間の限界を示した肯定側が優勢 |
| 尊厳の喪失 | 全介助状態は自己の喪失であり、自律性の問題 | 尊厳は主観的で基準にならない／傾聴で和らぐ | 長期の全介助への説得力で肯定側が優勢 |
| 精神疾患による不当な死 | 複数医師の審査があり、却下率も高い | うつの見落としが3〜5割ある／不可逆な死である | 発生確率が抑制されたと評価され、僅差で肯定側 |
| 周囲からの圧力による死 | 主たる動機は本人の尊厳喪失である | 家族への負担が実質的に死を強いる | 因果の連鎖が成立せず肯定側が優勢 |

同じデータから、時系列の帯としても、争点ごとの断面としても見せられる。どちらも判定を計算するものではない。人が Probability を決めるときに見る材料である。

# 10. 最終判定は HEnDA の枠組みを正本にする
v07では評価を三層に分ける。**L1 公式判定層**は HEnDA Judge Sheet と同じ語彙、**L2 内部分析層**は「なぜその評価なのか」を細かく追うための数値・イベント、**L3 ゲームHP層**は学習・観戦用の可視化である。三層を混ぜない。

| 層 | 役割 | 主な表現 |
|---|---|---|
| L1 Official Judge Layer | HEnDAの判定を支援する | Probability Hi/Lo、Value Large/Small、Strength Strong/Weak/None、Net sum、Voting Issue、Communication Points |
| L2 Internal Analysis Layer | P/Vの根拠とclashを追跡する | A/B/Cノード、Support Quality、Attack/Defenseイベント、Rule State、内部数値、counterfactual |
| L3 Game HP / Learning Layer | 変化を直感的に見せる | HP 0〜10、タイムライン、話者別デリバリー |

公式判定の中心は HEnDA Judge Sheet の Decision Making Chart に置く。

| 項目 | 公式表現 | アプリが支援すること |
|---|---|---|
| Issues | AD1 / AD2 / DA1 / DA2 | 主要論点を整理し、3つ目以降を除外候補にする |
| Probability | Hi / Lo | A/BリンクとSupport Quality、Attack/Defense後の成立度から候補提示 |
| Value (Impact) | Large / Small | Impactがどこまで説明・防御されたかを候補提示 |
| Strength | Strong / Weak / None | **Probability × Value** を内部で計算し、公式カテゴリへ写像する |
| Compare | AD合計とDA合計 | AI参考判定のNet sumを提示。ただし人間バロットとは分離する |
| Voting Issue | AD1等1つ | survival_candidate と clash_candidate の2候補から根拠付きで提示する |
| New Argument | Yes / No | Rule State Engine で採用可能な材料だけが判定に寄与しているか確認する |
| Communication | 1〜5整数 | 内容判定と分離した暫定提案。観測不能項目は人間確認に残す |

### Strength は第三の独立軸ではない

v07で最も重要な整理は、**Strength = Probability × Value** とすることである。Evidence、Warrant、Relevance、Burden は Strength にもう一度掛けず、Probability の理由として残す。公式画面では Hi/Lo・Large/Small・Strong/Weak/None を主表示し、内部数値は「AI参考判定の説明用」として明確に区別する。

### Voting Issue は「一番大きい論点」だけで決めない

Voting Issue は、次の二つを候補にする。

1. **survival_candidate**：最終時点で勝者側に残った論点のうち最も強いもの。
2. **clash_candidate**：その論点に対するAttack/Defense等のclashを取り除いて立論終了時へ戻したとき、最終marginを最も大きく動かすもの。

二つが一致すれば confidence は高い。一致しなければ両方を提示し、AIは「暫定候補」としてしか扱わない。勝者が反転するほど大きなclashだった場合は winner_flip として目立たせる。

### Value turn は無理に自動決着しない

「相手が良いと言った価値が、むしろ悪い」と反転する Value turn は、単なる Impact の減少とは違う。内部では Impact の大きさと向きを分けて記録するが、HEnDA Judge Sheet に存在しない signed score を公式表示へ持ち込まない。turn を入れるか入れないかでAI参考勝者が変わる場合は、**REVIEW_REQUIRED** として人間確認へ止める。

### Summary の新Evidenceは比較だけを助ける

既出のAD/DAを「どちらがより大きいか」「どちらが長く続くか」のように比較・整理するためのEvidenceは扱える。しかし、立論やDefenseで欠けていたObservation / Link / ImpactをSummaryで初めて埋めて成立させることはしない。これは **INADMISSIBLE_LATE_REPAIR** として判定材料から外す候補にする。

## 「小さい」と「ゼロ」は違う（v06から継続）

実試合の審査委員長は、否定側の二つの不利益について「ほぼ無視できるリスク」と述べた。同じ試合を客観的に評価した判定理由は、そこに異を唱えている。日本の精神科医不足も、オランダで安楽死された患者の一定数にうつ病の既往があった事実も、完全には消えていない。ゼロと見なすのではなく、「大幅に低くなった発生確率」と「現に苦しんでいる人を救う緊急性」を秤にかけるべきだ、という指摘である。

Judge Sheet の上では、この二つは区別がつかない。どちらも Strength: None と書けてしまう。そこで本アプリは、None にしたとき「何が残っていて、それでもなぜ勘定に入れないのか」を必須記録にする。書くのは点数ではなく理由である。
# 11. HP View：学習・観戦用に可視化し、公式判定とは分離する
L3では、内部分析層の Strength を **HP = 10 × Strength** として可視化する。たとえば AD1 がAttackで弱まり、Defenseで一部戻る様子をバーで表示する。

| Issue | Constructive | After Attack | After Defense |
|---|---|---|---|
| AD1 | ██████████ | ██████░░░░ | ████████░░ |
| DA1 | ██████████ | ███████░░░ | ███████░░░ |
| AD2 | ██████████ | ████████░░ | █████████░ |

HPは「HEnDAの公式得点」ではない。内部のカテゴリ判定を学習者へ説明するための表示であり、数値の写像や閾値は実試合で校正する。AIが直接「6.73点」と決めるのではなく、ノードやAttackを離散カテゴリで判断し、システムが決定的に数値へ写像する。

> **絶対に守る線引き**
> L3のHPから人間ジャッジの公式バロットを計算しない。逆に、人間の確定勝者からHPを逆算しない。HPはAI参考判定と学習分析の説明表示である。
# 12. AI と人間の役割分担
このアプリは「AI に任せる」設計ではなく、「AI で人間の判断を支える」設計である。v07では、AIが何を数値化してよいか、どこで止まるべきかも役割分担に含める。

| AI が行うこと | システムが行うこと | 人間が行うこと |
|---|---|---|
| 文字起こし候補、A/B/C抽出、Support Quality、Attack/Defense/Rule State候補、離散カテゴリ、Decision Supportの説明ドラフト | カテゴリ→数値写像、Strength=P×V、Net sum、counterfactual、Review Gate、履歴・版管理 | 聞き取れた内容の確認、境界事例の採否、公式Probability/Value/Strength、Winner、Voting Issue、Communication等の最終確定 |

AIはカテゴリと根拠位置・理由・confidenceを出す。小数値・閾値・計算式はscoring_configに固定し、同じ入力なら同じ数値になるようシステム側で処理する。AIの再実行で勝手に確定済みバロットを書き換えない。

さらに、次の条件ではAIは一方の勝者を断定しない。

- 重大な UNVERIFIABLE / 記録欠損が勝敗へ影響し得る。
- Value turn の採否で勝者候補が変わる。
- Voting Issue の survival_candidate と clash_candidate が競合し、説明confidenceが低い。
- Summary の新Evidenceが comparison なのか late repair なのか境界的である。

この場合、画面に **REVIEW_REQUIRED（要確認）** と根拠位置を出す。

## 表現力への評価と、議論への評価を分ける（v06から継続）

実試合の審査委員長は、肯定側の勝因として「心に刺さる生々しい描写」と「患者への共感を呼んだ表現力」を挙げた。同じ試合を客観的に評価した判定理由は、同じ結論を別の言葉で書いている。感情的な説得力ではなく、自律性という権利の議論と、「傾聴で解決できる」という反論への有効な再反論を根拠として評価すべきだ、というものである。

どちらが正しいかを本アプリが決めることはしない。判定理由の段落を content / comparison / procedure / delivery / advice に分け、deliveryがVoting IssueやStrengthの理由へ入り込んでいれば、人へ知らせる。学習用デリバリー分析は話者別に行えるが、L1の内容判定へは入れない。
# 13. 「空白」には三つの意味がある（v06で新設）

実試合の書き起こしでは、10分25秒がひとつの区間になっていて、その中にあるはずのスピーチ2つ分の内容が失われていた。両チームとも実際には話しているのに、記録には何も無い。

このとき画面には空白が表示される。しかし空白には、まったく違う三つの理由がある。

| 空白の理由 | 意味 | 判定での扱い | 直し方 |
|---|---|---|---|
| 記録が無い | 音声そのものが欠けている、または区切りを取り違えた | 判定材料にしない。この範囲を根拠に判定を確定できない | 音声を入れ直す、境界を引き直す |
| 聞き取れなかった | 音はあるが、ジャッジが実際には聞き取れなかった | 判定材料にしない。試合後に原稿を読んで補うことはしない | 聞き直す。それでも駄目なら「聞き取れなかった」として確定する |
| 応答しなかった | 相手の主張に答える機会があったのに、答えなかった | 判定材料になる。ジャッジが重みを決める | 直すものではない。試合で起きた事実である |

v05は二つ目と三つ目しか持っていなかった。この状態で実試合を処理すると、否定側が自陣の不利益をすべて放棄し、肯定側は総括をしなかった、という記録が機械的に生成される。どれも事実ではない。

> **なぜこれがコンセプトの話なのか**
> 三つを混ぜることは、単なるバグではない。「議論に答えなかった」は競技上の失点であり、選手の評価に直結する。記録の欠落をそれとして残すのは、起きていないことで選手を不利にすることである。
> 本アプリは判定支援ツールである。判定を支援する道具が、誤った判定材料を静かに作り出してはならない。

> **「聞こえなかった」を尊重する（v05から継続）**
> ジャッジが試合中に聞き取れなかった発言は、あとから原稿や文字起こしを読んで判定材料に補わない。解析用には内容を残せても、Judge View では「聞き取れなかった」として扱う。さらに、聞き取れなかったと確定した発言を判定の根拠に引いたままでは、判定を確定（ロック）できない。画面はその発言へ直接案内し、根拠から外すか、聞き直すかを促す。記録が無い区間も同じ扱いにする。

# 14. 判定は一つではない（v06で新設）

実試合の決勝は5人の審判が審査し、結果は4対1だった。審査委員長は自分の判断だけでなく、「ほとんどのジャッジがこう考えた」という形で講評を述べている。

v05のコンセプトには、この形が無かった。1試合につき1つの判定を作り、それを説明する、という前提だった。

| 概念 | 意味 |
|---|---|
| バロット | ジャッジ1人ぶんの判定。勝敗、Voting Issue、Communication、判定理由をすべて含む |
| パネル | ひとつの試合を審査するジャッジの集まり |
| パネルの結果 | バロットの多数決。集計するだけで、個々のバロットを書き換えない |
| 少数意見 | 多数と違う判断をしたバロット。消さない。判定理由もそのまま残す |

- ふだんの運用ではジャッジは1人である。校内練習でも、個人のジャッジ研修でもそうである。パネルはそれを一般化した形であって、複数人を強制する仕組みではない。
- 4対1の「1」が消えると、残るのは「肯定側が勝った」という結論だけになる。しかし研修と研究にとって価値があるのは、5人が同じ試合を見て、なぜ1人だけ違う結論に至ったかのほうである。
- 同じ試合について、勝敗が一致していても Voting Issue が違うことがある。これも記録する。「どの論点で決めたか」の分布は、指導の材料として結論そのものより有益である。

> **これは Phase C の前倒しではない**
> v05の Phase C は「熟練ジャッジの解説を参照データにする」ものだった。§14はそれとは別で、通常の判定記録の形の話である。ジャッジが1人でも成立し、複数人になっても壊れない形にしておく、というだけである。

# 15. 誰が、何のために使うのか

| 利用者 | 使い方 |
|---|---|
| ジャッジ | フロー作成、論点整理、判定理由の確認。短時間で見落としを減らす |
| 顧問・指導者 | 試合後レビュー。「どこが崩れたか」を元発言と一緒に説明する |
| 高校生・初心者 | Attack / Defense / Summary の意味と、勝敗の決まり方を学ぶ |
| 観客 | 試合中にどちらの議論がどう変化したかを追いやすくする |
| 大会運営者 | 許諾済み試合を記録・教材化し、ジャッジ間の判断比較にも使う |
| 研究・開発 | AI と人間ジャッジの一致・不一致、ジャッジ同士の一致・不一致、学習効果を検証する |

同じ議論データを、ジャッジ支援・教育・観戦・研修へ使い回せることが大きな特徴である。別々のアプリを作るのではなく、同じ「議論の地図」を用途別に見せ方を変える。

# 16. 1試合から残る7つの成果物
| 成果物 | 何が残るか | 主な用途 |
|---|---|---|
| 1. タイムスタンプ付き逐語記録 | 各発言と音声・動画の位置、役割、Stage、記録欠損 | 確認・検証 |
| 2. デジタル Flow Sheet | Claim / Evidence / Attack / Defense / Summary とA/B/Cノードのつながり | 議論追跡・学習 |

| 4. 人間 Judge Sheet / Ballot | 人が確定したProbability / Value / Strength、Winner、Voting Issue、Communication | 公式運用・記録 |

v07では、AIの参考判定と人間のバロットを成果物レベルでも分離した。AIが出した数値や候補が、そのまま「ジャッジの公式判断」に見えないようにするためである。
# 17. このコンセプトの独自価値
「AI がディベートを判定する」だけなら、勝敗予測や採点で終わる。本構想は、判定に至る過程そのものをデータ化し、説明し、必要なときには止まれることを価値の中心に置く。

| 価値 | 本アプリで実現すること |
|---|---|
| Traceable / 追跡できる | 判定理由から元の発言・時刻へ戻れる |
| Explainable / 説明できる | 「何が効いたか」をA/B/C・Attack・Defense・Summaryの流れで説明できる |
| Rule-aligned / 競技ルールに沿う | HEnDA Judge Sheetの語彙と採用可否を正本にする |
| Layered / 層を混ぜない | 公式判定、内部分析、ゲームHPを分離する |
| Human-controlled / 人が決める | AIはDecision Support、人間がバロットを確定する |
| Conservative / 無理に断定しない | Value turn、欠損、境界事例ではREVIEW_REQUIREDを出す |
| Auditable / 再計算できる | scoring_config、イベント台帳、counterfactual、モデル版を保存する |
| Honest about gaps / 分からないことを残す | 記録欠損・unheard・未応答・unverifiableを混ぜない |
| Plural / 判断の違いを残す | 複数ジャッジの判定と理由を保存する |
| Reusable / 学習へ再利用できる | 同じ試合を選手指導・ジャッジ研修・観戦解説・研究へ展開できる |

> **差別化を一文で**
> 「AIが勝敗を出すジャッジ」ではなく、**HEnDAの判定過程を、公式語彙・内部分析・学習可視化の三層で再現し、どのclashが勝敗を動かしたかまで説明できる判定支援基盤**。
# 18. 許諾と保持：誰のデータを、いつまで持つか

このアプリが扱うのは、多くの場合、未成年である高校生の音声と氏名である。便利さを先に追ってここを曖昧にすると、プロジェクトそのものが止まる。だから許諾と保持を「運用の心がけ」ではなく、アプリの機能として持つ。

まず、試合ごとに許諾の範囲を記録する。範囲は4種類あり、何に使ってよいかが変わる。

| 許諾の範囲 | 何に使えるか |
|---|---|
| 校内練習 | 本人・チーム・顧問による振り返り。外部には出さない |
| 研修教材 | ジャッジ研修や指導教材として、試合の当事者以外にも見せる |
| 研究 | 一致率や学習効果の検証に使う。氏名は残さない |
| 熟練ジャッジ参照 | 熟練者の解説を参照データにする。通常の録画許諾には含まれないため、別に取る |

次に、保持するデータを5つの層に分ける。「音声を消す」と「氏名を消す」と「判定を消す」は別の操作であり、試合ごとに期限を決められる。

| 層 | 中身 | 消すと失われるもの |
|---|---|---|
| A 音声・動画 | 録音・録画そのもの | 原音で聞き直すこと。聞き取れたかの判断のやり直し |
| B 逐語記録 | 発言の本文 | 誰が何を言ったかを読むこと |
| C 氏名 | 選手名・Best Debater 欄・名乗りの区間 | 誰の試合かの特定 |
| D 議論と判定 | Flow・Judge Sheet・判定理由 | 議論の構造と判定の記録 |
| E 匿名統計 | 試合数、ステージ長、フラグ件数 | （最後まで残す層） |

- 削除は A → B → C → D の順にしか進めない。氏名だけを先に消して音声を残す、はできない。スピーチには必ず名乗りが入るので、音声が残っていれば氏名は復元できてしまうからである。
- 研修教材や研究として登録した試合は、解析が終わった時点で A・B・C をまとめて消す。中途半端な状態を作らない。
- 消した層は画面に「削除済み」と表示する。空欄にして「もともと無かった」ように見せない。
- 本文中の人名は自動で置き換えない。名乗りは消すべきだが、証拠として引用された専門家の氏名は消してはいけない。機械にはこの区別がつかないので、名乗りの区間を人が印付けする。

実試合を読んで一つ分かったことがある。名乗りは二か所にあった。開会の自己紹介と、各スピーチの冒頭である。片方だけを伏せても、もう片方が残っていれば氏名は分かる。両方を印付けの対象にする。

そして、氏名を消しても競技上の記録は完全に残る。A1 が立論し、A3 がディフェンスを担当したという情報は、氏名とは独立している。画面が最初から座席と役割で動いていれば、氏名を消しても何も壊れない。

# 19. このアプリが「しないこと」
- AI の参考判定を、人間ジャッジの最終バロットとして自動確定しない。
- HEnDA の公式表示を、独自の100点満点へ置換しない。内部分析用の数値は「AI参考・校正対象」として別層に置く。
- Strength を Probability / Value と並ぶ第三の独立係数にしない。**Strength = Probability × Value** を守る。
- Evidence / Warrant を Probability と別にもう一度掛けて二重評価しない。
- 聞き取れなかった発言や記録欠損を、後から文字情報で補って公式判定根拠にしない。
- Value turn や境界的なNew Argumentで勝敗が変わり得るのに、AIが無理に一方の勝者を断定しない。
- Summary の新Evidenceで、立論・Defenseで欠けた因果リンクを後付け修復しない。
- 複数ジャッジの判定を一つに丸めて少数意見を消さない。
- 表現力への評価を、そのまま内容論証のStrengthへ混ぜない。
- 声の特徴からの話者推定を、HEnDA担当表や自己紹介による座席確定より優先しない。
- 公開動画の無断取得や、許諾のない試合の教材化を前提にしない。

この「しないこと」を明示することで、AIの派手さよりも、競技としての公平性・検証可能性・教育利用の信頼性を優先する。
# 20. 段階的な発展イメージ
| 段階 | 中心機能 | 価値 |
|---|---|---|
| Phase A0：1試合縦切り | A/B/C、Support Quality、Attack/Defense台帳、P/V/Strength、Decision Support | 評価ロジックを1試合で端から端まで検証する |
| Phase A1：パイロット | 10試合。Rule State、Voting Issue二候補、Review Gate、Human Ballot比較 | ルーブリックとデータ構造の欠陥を発見する |
| Phase A2：校正 | 30〜50試合。カテゴリ→数値、閾値、weakest_link/product等を校正 | AI参考判定を人間ジャッジの判断へ近づける |
| Phase A3：ホールドアウト | 別20〜30試合。パラメータを固定して性能を報告 | 過学習ではないかを検証する |
| Phase B：学習・観戦可視化 | Debate Evolution、Clash View、HP View、初心者向け解説 | 議論の変化を直感的に理解できるようにする |
| Phase C：熟練ジャッジ参照 | 許諾済み実試合と熟練ジャッジ解説、複数バロット比較 | AI候補の改善、研修教材、判断差の研究に使う |

> **校正の考え方**
> 「勝敗が合ったか」だけで評価しない。Probability / Value / Strengthのセル一致、Voting Issue候補包含、Attack種別、Rule State、Communication Points、説明の納得性を別々に測る。

> **実試合の突き合わせは段階ではなく習慣にする**
> 合成データでは欠損、少数意見、表現力混入、Value turnのような境界事例が出にくい。機能を足す前に実試合を読み、設計入力として記録する。
# 21. 教育・観戦・大会プラットフォームとの関係

この解析・ジャッジ支援は、英語ディベート教育・大会プラットフォーム全体の「判断エンジン」として位置づけられる。

| 面 | 内容 |
|---|---|
| Judge | 試合を追い、判定理由を整理する |
| Learn | 過去試合から Attack / Defense / Summary を学ぶ |
| Watch | HP や Debate Evolution で観戦を分かりやすくする |
| Coach | 指導者がターニングポイントを使って振り返る |

つまり、将来の観戦型ゲームや初心者教育を支える前に、「議論を正しく構造化し、判定過程を説明できる」ことが土台になる。先に解析基盤を作る理由はここにある。

# 22. 完成したときの理想的な体験
試合終了後、ジャッジや生徒が画面を見ると、次のように理解できる状態を目指す。

1. AD1/AD2/DA1/DA2 が Observation / Link / Impact に分解されている。
2. 「どのAttackが、どのノードを狙ったか」が一目で分かる。
3. Defenseで何が回復し、何が回復しなかったかを元発言へ戻って確認できる。
4. Evidence / Warrant / Relevance / Burden が、Probabilityの理由として説明される。
5. Summaryがどの比較軸を使い、comparisonなのかlate repairなのかが区別される。
6. 最終Strengthだけでなく、どのclashがmarginを最も動かしたかが分かる。
7. Voting Issueはsurvival_candidateとclash_candidateの両方が見え、人間が最終確認できる。
8. Value turnや記録欠損で自動断定できないときは、REVIEW_REQUIREDと理由が表示される。
9. AI参考判定と人間バロットが別々に残り、複数ジャッジなら少数意見も読める。
10. 学習モードではHPやタイムラインで、同じ議論を初心者にも直感的に見せられる。

> **ゴール**
> 「勝者：AFF」と表示して終わるのではなく、**なぜAFFが勝ったと考えられるのか、何をAIが推定し、何を人間が確定したのか、どの発言が決定的だったのかを第三者が追跡できる**状態を作る。
# 23. コンセプトの最終整理
本プロジェクトの核は、英語ディベートを単なる音声や文章の集合ではなく、「時間とともに変化する議論の構造」として扱うことである。v07では、その構造を**公式判定・内部分析・学習可視化の三層**へ分け、AIが説明できる範囲と、人間へ返すべき境界を明確にした。

> **コンセプト・ステートメント**
> 英語ディベートの「聞く・追う・比べる・決める」を、HEnDA Judge Sheetと整合する形で可視化する。AIは論点の構造とclashを解析し、Decision Supportを提示するが、最終バロットは人間が確定する。判断材料が足りないときは無理に答えず、要確認として根拠箇所へ戻す。

この土台ができれば、ジャッジ支援、初心者教育、指導者の振り返り、観戦型ゲーム、熟練ジャッジ研修を、同じ議論データから発展させられる。
# 付録. 初めて読む人のための用語ミニ辞典

| 用語 | 意味 |
|---|---|
| AFF / NEG | Affirmative（肯定側）／Negative（否定側） |
| AD / DA | Advantage（肯定側の利点）／Disadvantage（否定側の不利益） |
| Flow Sheet | 試合中の主張・反論・再反論の対応関係を記録する表 |
| Evidence | 主張を支える根拠・引用資料 |
| Warrant | Evidence から Claim へつなぐ理由づけ |
| Attack | 相手の議論の弱点を特定して攻撃するスピーチ |
| Defense | Attack に答え、自分の議論を再構築するスピーチ |
| Summary | 試合全体の重要論点を整理し、双方を比較する最終スピーチ |
| Impact / Value | その結果がどれほど重要・重大か |
| Solvency | その計画で本当に問題が解決するか。「対象者に届くか」もここに含まれる |
| Uniqueness | その計画でなければ得られないか。既存の手段で足りるなら固有性が下がる |
| Clash Point | 試合の中で双方が正面からぶつかった主要な争点 |
| New Argument | 相手に十分な反論機会がない後半で新しく持ち込まれた議論 |
| Voting Issue | ジャッジの投票を最も決めた主要論点 |
| Ballot / バロット | ジャッジ1人ぶんの判定。勝敗、Voting Issue、判定理由を含む |
| Panel / パネル | ひとつの試合を審査するジャッジの集まり。結果が割れることがある |
| Split Decision | ジャッジの判断が分かれた判定。たとえば5人中4対1 |
| Audibility | その発言をジャッジが実際に聞き取れたかどうかの記録。AI の自信度とは別物 |
| 記録の欠損 | 音声そのものが無い、または区切りを取り違えて内容が失われた範囲。聞き取れなかったのとは別 |
| 名乗りの区間 | スピーカーが自分の名前を述べた部分。座席と氏名を結び付ける唯一の手掛かりであり、匿名化のときに伏せる対象 |
| 許諾（Consent） | 録音・利用について本人・保護者・学校から得た同意。範囲を試合ごとに記録する |
| 保持レベル | 音声・逐語記録・氏名・議論と判定・匿名統計の5層。層ごとに消せる |
| Support Quality | Evidence / Warrant / Relevance / Burden。Probabilityの評価理由を説明する内部タグ |
| Rule State | 発言を判定材料として採用できるかを、スピーチ種別と事象種別から管理する状態 |
| Late Repair | Summaryで初めて欠けた立証を補い、既存論点を後付けで成立させようとすること。判定材料にはしない |
| survival_candidate | 最終的に勝者側に強く残ったVoting Issue候補 |
| clash_candidate | Attack/Defense等を取り除く反実仮想でmarginを最も動かすVoting Issue候補 |
| clash leverage | その論点のclashが最終marginをどれだけ動かしたかを示す内部分析値 |
| Value turn | 相手が「良い」と置いたImpactの価値方向を反転させるAttack |
| REVIEW_REQUIRED | AIが一方の勝者を断定せず、人間確認へ止める状態 |
