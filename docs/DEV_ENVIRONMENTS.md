# DEV_ENVIRONMENTS.md — どこで実装し、どこで確かめるか

## 0. 前提の整理

**製品が特定のPCに依存しないこと**と、**エージェントがどこで走るか**は別の話である。

- 守るべきは前者。CIが唯一の判定者であり、リポジトリが手元の環境を前提にしない。
- 後者は道具の使い分けにすぎない。Web版とデスクトップ版は同じリポジトリに対する2つの入口であり、
  どちらを使っても、上の一線を守る限り設計は壊れない。

このファイルは、その使い分けを決める。

---

## 1. クラウドセッションに何が入っているか

Claude Code on the web の各セッションは Ubuntu 24.04（x86_64）のVMで、
リポジトリがクローンされた状態で始まる。

| 項目 | 内容 |
| --- | --- |
| リソース | 約 4 vCPU / 16 GB RAM / 30 GB ディスク |
| Node.js | 20 / 21 / 22（既定は22）、npm / yarn / pnpm、eslint、prettier、chromedriver |
| **データベース** | **PostgreSQL 16、Redis 7.0**（プリインストール。既定では未起動） |
| コンテナ | docker / dockerd / docker compose |
| ユーティリティ | git、gh、jq、ripgrep、tmux |
| ネットワーク | 既定は **Trusted**（npm・GitHub・Docker Hub・Ubuntu等の許可リストのみ） |

**PostgreSQL 16 がセッション内にあることが、この案件では決定的である。**
マイグレーション、RLSポリシー、トリガー、CHECK制約の検証は、
本物の Supabase に接続せずセッション内で完結する。

---

## 2. 実 Supabase には接続しない（確定）

### 2.1 理由

1. **技術的に通らない可能性が高い。** クラウドセッションの外向き通信はHTTP/HTTPSプロキシを通る。
   Supavisor への接続は Postgres ワイヤプロトコル（6543番）なので、許可ドメインに足しても届かない見込み。
2. **通っても、やるべきではない。** エージェントが実データベースを直接触れる状態を作らない。
3. **不要である。** セッション内の Postgres 16 で同じ検証ができる。

### 2.2 代わりにこうする

| やること | どこで |
| --- | --- |
| マイグレーションの作成と検証 | クラウドセッション内の Postgres 16 |
| RLS・トリガー・CHECK制約のテスト | 同上 |
| **本番/ステージング Supabase へのマイグレーション適用** | **GitHub Actions**（Secretsに `DIRECT_URL` を置く） |
| Supabase Storage / Auth の動作確認 | デスクトップ、または人の手 |

**リポジトリが「生きた Supabase があること」を前提にしない。**
これはクラウド完結のためだけでなく、テストの再現性のためにも正しい。

---

## 3. シークレット方針

クラウド環境には**専用のシークレットストアがなく**、環境変数はその環境を使う人全員から読める。
公式ドキュメントも、APIキーや認証情報を入れないよう明示的に警告している。

| 種類 | 置き場所 |
| --- | --- |
| 転写プロバイダのAPIキー（Pass A / B） | GitHub Actions Secrets、またはデスクトップの `.env.local` |
| 解析・判定支援LLMのキー | 同上 |
| `SUPABASE_SERVICE_ROLE_KEY` | 同上 |
| `DIRECT_URL`（本番マイグレーション用） | GitHub Actions Secrets のみ |
| セッション内Postgresの接続情報 | ダミー値でよい。SessionStart フックが生成する |

**結論として、クラウド環境の設定にはシークレットを1つも置かない。**
その結果、ネットワークアクセスは既定の **Trusted のままでよい**（Custom 許可リストを作る必要がない）。

実プロバイダを叩くPR（P5・P8）だけが例外で、それはデスクトップかCIで動かす。

## 5. セッション内Postgresの落とし穴

**テーブルの所有者はRLSを素通りする。**
`app_migrator` がテーブルを所有し、`app_server` には `GRANT` だけを与える構成にすること。
所有者と接続ロールを同じにすると、RLSのテストが「通ったように見えて何も検証していない」状態になる。

念のため `ALTER TABLE ... FORCE ROW LEVEL SECURITY` も併用する。

```sql
-- SessionStart フックが作る構成
CREATE ROLE app_migrator LOGIN NOSUPERUSER;   -- テーブル所有者
CREATE ROLE app_server   LOGIN NOSUPERUSER NOBYPASSRLS;
-- マイグレーションは app_migrator で流し、アプリは app_server で接続する
```

これは本番の Supabase と同じ構成なので、ここで通ったRLSは本番でも同じように効く。

## 6. クラウド環境の設定

### 6.1 環境ダイアログに入れるもの

claude.ai/code の環境セレクタから設定する。

| 項目 | 値 |
| --- | --- |
| 名前 | `ai-debate-analyzer` |
| ネットワークアクセス | **Trusted**（既定のまま） |
| 環境変数 | **なし**（シークレットを置かない方針のため） |
| セットアップスクリプト | `scripts/setup-cloud-env.sh` の内容を貼る |

セットアップスクリプトはUI側に持つ設定だが、**内容はリポジトリにも置いて版管理する**。
両者がずれたときに気づけるよう、CIで内容を突き合わせる。

### 6.2 制約

- セットアップスクリプトは**終了コード0**でなければセッションが起動しない。
  重要でないコマンドには `|| true` を付ける。
- **5分以内**に終える。超えると環境キャッシュが作られず、毎回走ることになる。
- キャッシュはファイルシステムのスナップショットなので、**起動したプロセスは残らない**。
  Postgresの起動などは SessionStart フック側で行う。
- キャッシュは、スクリプトや許可ドメインを変えたとき、および約7日で作り直される。

## 7. ファイル

| ファイル | 役割 | 実行される場所 |
| --- | --- | --- |
| `scripts/setup-cloud-env.sh` | VMの下ごしらえ（プリインストールにないもの） | クラウドのみ・Claude Code起動前・キャッシュ有効時はスキップ |

`~/.claude/` に置いた設定はクラウドセッションに届かない。**リポジトリの `.claude/` に置くこと。**

## 8. 守るべき一線

デスクトップ版を使うこと自体は設計に反しない。破ってはいけないのは次だけである。

- **CIが唯一の判定者。**「手元では通った」を根拠にしない。
- 絶対パス、ローカル専用スクリプト、手元にしかないファイルをリポジトリの前提にしない。
- 本番の認証情報は GitHub Actions Secrets にだけ置く。
- クラウド環境の設定にシークレットを置かない。

> whosaid-editor は `C:\dev\01` 配下であること、`.venv` を有効にすること、
> ffmpeg が WinGet で導入済みであることを前提にしていた。
> あれを再発させないための一線である。
