## 1.5 確定事項【本文書の中核】

### A. 同点の扱い — 「判定不能」から「推定により否定側」へ

**demo の実装（誤り）**: v20 §8 ① で「同点の場合、エンジンは判定を出さない。人が確認して確定する」と確定していた。

**規定**: 4.2 は引き分けを認めていない。拮抗して見えても安易に同等とみなすことは許されず、細かい差を検証してどちらかに勝ちを付けよと命じたうえで、どうしても優劣がつけられない例外的な場合は**推定（presumption）に基づき否定側の勝利**とする。複数ジャッジの場合も各自が必ずどちらかに投票し、引き分けはないと明記されている。

**確定**:
- 両側の合計が等しいとき、**判定は否定側とする（規定 4.2 の推定による）**
- 判定根拠を「推定による」と明示し、人の確認を要する印を付ける
- demo の設計意図（機械が勝手に確定させない）は救われる。意図は「判定を出さない」ことではなく「人が検証して確定する」ことだった
- **この推定は最終判定にのみ働く。** 個々の論点が拮抗していても否定側に倒さない
- judge-support としてはむしろ価値の高い出力になる。人間ジャッジが最も迷う場面を名指しして渡すことになるため

### B. ディフェンス・総括での資料の扱い — 関門の前置

**demo の実装（不十分）**: v20 §9 で規定確認を次版に持ち越し、暫定的に「新しい議論は禁止、既存議論の資料による補強は可」という立場を採っていた。

**規定**: 4.2.2 は「新しい議論」として無視する対象に、**総括やディフェンスで相手チームの Advantage・Disadvantage の証明に対して新しいアタックの証拠資料が出た場合**を含めている。一方 2.1.5／2.1.6 はディフェンスの役割を「相手のアタックが無効であることを論じ、自陣の議論を再構築（reprove）すること」と定める。2.1.7／2.1.8 は総括での新しいアタックを禁じつつ、細かい証拠比較や大きな視点からの比較は許す。4.2.2 も「双方の議論をより深い角度から比較するような言及や証拠資料」は無視してはならないと明記。

**読み取れる線引き**: 禁じられているのは**資料の新しさ**ではなく、**その資料が相手への新規アタックとして働くこと**。自陣の議論を守り直すための資料提示は 2.1.5 の「再構築」そのもので、当然に許される。demo の「全回復＝攻撃の核心に資料を伴って応答」という定義は、そのままでは規定違反の行為に最高評点を与えうる状態だった。

**確定**:
1. **回復幅の判定の前に「資料の働き」の関門を置く。** 自陣の議論の再構築に向いていれば有効な防御として回復幅の判定に進み、相手の証明を新たに突くものなら 4.2.2 により無視して回復を与えない
2. 判定基準は**その資料が反論している対象**で切る。相手のアタックが突いた自陣の弱点を埋める資料なら再構築、相手の立論の証明を直接崩しにいく資料なら新規アタック
3. **「全回復」の定義から資料要件を外す。**「攻撃の核心に応答し、自陣の議論を再構築した。資料を用いる場合は、それが自陣の再構築に向けられていること」
4. **防御側の分類に「新規アタックとして無視」を追加する。** その部分は判定から除外され回復は生じない。到達点は攻撃後の値のまま
5. **同じ適格性判定を総括の比較主張にも適用する。** 比較を制したと判定する前に、根拠となった発言が比較として適格かを確かめる。不適格なら重みは動かさない（**demo に無い要素。analyzer で新規に設計する**）

なお demo が v20 §3.7 で 3:14 の台詞を「読み返す時間がない」に変えた判断は、結果として規定に沿っていた。立論資料を引き直して自陣の調査範囲を示すのは再構築であり、規定上問題ない。

### C. RUBRIC の尺度重なり — 「移さない」ことで回避する

**demo の既知欠陥（v20 §9）**: ①尺度 8/7・7/6・6/5 の条件が排他でない。②尺度 4・3・2 が攻撃到達点と二重定義。`scaleNote` の断り書きで計算上の破綻は回避しているが、記述と値が食い違う例が既に出ている。

**原因の診断**: **10点尺度という一本の道具に性質の違う二つの仕事をさせている**ために生じている。立論の初期評価は絶対評価、攻防後の値は相対的な移動。同じ目盛りに載せれば衝突は必然。

**確定**:
- **攻撃到達点と防御回復幅の体系だけを移す**（§1.5-B の修正を織り込んだ形で）
- **立論の10点尺度は移さない。** analyzer 側で**条件ベースの初期評価**として設計する。充足条件のチェックリストとして持ち、点数はそこから導出する
- **攻防による移動は初期値と独立したイベント列**として記録する。demo の `hist` が既にこの形
- **重なり問題は「持ち越す」のではなく「移さないことで発生させない」**
- この設計作業は §9.11 のラウンドで行う

### D. 判定の二層構造 — 内部要素と判定軸を分ける【v04 で訂正】

**v03 の誤り**: Present Situation / Effect / Impact の三論点をそのまま判定軸に据え、Σ(d_k × w_k) の**和**で集計していた。これは**議論の内部構造と判定軸を混同している**。

**HEnDA の正しい構造**:

公式 Judge Sheet の判定軸は次の形である。

```
Probability（蓋然性） × Value / Impact（価値・重要性） ＝ Strength（議論の強さ）
```

一方、立論の構成は `Present Situation → Effect → Importance (Impact)`。**Effect はジャッジの独立した最終評価軸ではなく、立論を構成する要素**である。「プランを実施すると、本当にその変化・利益／不利益が起こるのか」を示す部分であり、**Effect が崩れると Probability が下がる**という下位関係にある。旧来のジャッジ基準でも、Probability は「メリットが確実に得られるか」を見るもので、Attack 後に回復できなければゼロにもなり得るとされる。

**確定: 二層構造とする。**

```
【内部分析層】攻防イベントが着弾する場所
  Present Situation → Effect → Impact
        ↓ Attack / Defense を経てどれだけ残ったか

【判定層】公式 Judge Sheet の軸
  Probability × Impact(Value) = Strength
```

- **Present Situation と Effect は Probability に集約される**（2対1）。現状に問題が存在しなければメリットは得られず、プランが効果を生まなければやはり得られない。どちらも「確実に得られるか」を左右する。Disadvantage 側も同じで、固有性が崩れればプランから生じる話ではなくなり、リンクが切れれば発生しない
- **Impact は独立した軸としてそのまま判定層へ上がる**
- **Effect・Impact・Probability を横並びの同格評価にしてはならない。** Effect は Probability を決める下位要素、Impact は独立したもう一方の軸

**確定: 集計は積とする。論点ごとに Strength = Probability × Impact。**

これは demo からの最も大きな変更である。demo は次元をまたいだ**和**（Σ d_k）で集計していたが、公式は**積**である。違いは無視できない。

- 積であれば、Probability がゼロに近づけば Impact がいくら大きくても Strength はゼロに落ちる。「Attack 後に回復できなければゼロにもなり得る」という規定上の挙動は、**積だからこそ表現できる**
- 和のモデルではこれが出せない。Impact 9・Probability 1 の議論が、和なら合計10 で残ってしまう

**【要検算】demo の判定結果は積で計算し直すと変わりうる。** demo の数値例では否定側の発生可能性が 7→2 まで落ちたのに Impact 8 がそのまま残って合計を支えていた。積で計算すればその Disadvantage の Strength は大きく落ちるはずである。demo の「否定側 3.5点差」という結論そのものが、積モデルでは再現されない可能性が高い。**demo の検算表を受け入れ基準にそのまま流用してはならない。**

### E. Probability の合成 — 鎖の弱い環が決める【v04 新設】

**確定: Probability = min(Present Situation, Effect)**

**理由**: 規定 2.1.1.3 は三論点を「客観的に示すことが求められます」と並列に課しており、どれかが強ければ他を補える、とは書いていない。証明されていない環があれば、そこで鎖は切れる。現状に問題が無ければ効果があっても意味がなく、逆も同じ。

**副次的な利点**: どの環が全体を決めているかが計算結果から直接読める。「この Advantage の Probability を決めているのは Effect の側で、Present Situation はそれより高い」と言える。積や加重平均では両方が薄く効いて原因が特定しにくい。judge-support としては min の方が説明力がある。

**注意**: min は情報を捨てるので、**捨てた側の値も記録に残す**。Present Situation 8・Effect 3 で Probability 3 となったとき、Effect が防御で回復すれば Probability は 8 まで戻りうる。感度分析の対象としても、どちらの環が効いているかは保持すべき情報である。demo の `hist` が要素ごとに推移を持つ設計なのでそのまま対応できる。

### F. 重みの適用単位 — 論点単位に畳める【v04 で整理】

**Strength = P × I のとき、P に1.5を掛けても I に1.5を掛けても、Strength への効果は同じ1.5倍になる。** つまり重みは数値上、**その論点の Strength にかかるのと等価**である。

**確定**:
- 計算上、重みは**論点単位**で適用する（軸ごとに分けて掛ける必要はない）
- ただし**どちらの軸で比較が争われたかは説明として記録する。**「相手のデメリットは起きない」と論じて Probability の土俵で制したのか、「我々のメリットの方が重い」と論じて Impact の土俵で制したのかは、判定理由として本質的に違う情報である。数字としては同じ効果でも、説明生成には必須
- 重み: 優位側が制した→1.5 / 劣位側が制し返した→0.5 / 決着なし・土俵外→1.0
- §1.5-B-5 の適格性判定を前置する

### G. 複数論点への一般化 — 側ごとの重み付き総和

**規定**: 各 side 最大2つの Advantage / Disadvantage（2.1.1.3／2.1.2.1）。規定 4.2 が求めるのは「Advantage の総和が Disadvantage の総和を上回るか」の判断。

**確定1: 側ごとに重み付き Strength の総和を取り、比較する。**

```
肯定側合計 = Σ(各 Advantage の Strength × その論点の重み)
否定側合計 = Σ(各 Disadvantage の Strength × その論点の重み)
判定は両者の比較による（差が0なら §1.5-A により否定側・推定）
```

demo の `judge()` は既に側ごとに合計を出す形（`wa`/`wn`）を持っている。1対1では差の計算と同値になるので違いが見えなかっただけで、**側ごとに集計する骨格は流用できる**。ただし各論点の値の求め方は §1.5-D/E のとおり積と min に置き換える。

**確定2: 重みの適用は、総括の比較主張が名指しした粒度に従う。**

総括が Advantage-1 と Disadvantage-1 を名指しで比べたなら、その2論点に重みがかかる。論点を特定せず全体の比較を述べたなら、両側全体にかかる。比較主張の粒度を記録しておけば重みの適用範囲も決まる。comparison_events が論点対を持てる設計ならそのまま乗る。

**確定3: 論点数の上限判定は保留の対象とし、主要2つの選択は人に回す。**

規定 4.2.1 は、実質的に2つを超える言及があった場合、ジャッジは主要と考える二つ以外を無視するとする。2.1.1.3 は、一つの Advantage に二つ以上の異なる事柄が混ざっている場合は別の Advantage に分けよとも定める。「1つの論点か、2つが混ざっているか」の判断は自動化が難しく、主要2つの選択はジャッジの裁量なので、保留として人に回す。

### H. 資料の裏づけ — 独立軸にせず各内部要素に織り込む

**demo の扱い**: 5観点の一つとして独立に持っていた。ただし総括比較では土俵外に置いており、**demo 自身、他の観点と同列に扱えていなかった。**

**規定**: 資料の裏づけは独立した証明論点ではない。2.1.1.3 が求めるのは三論点で、資料はそれぞれを証明する手段。3.1 は「証拠資料を引用しているかいなかだけで試合の勝ち負けが決まるわけではない」「資料を引用したとしても質の低い資料の場合、効果はありません」と述べる。3.1.3 も、原文を見せられない場合にジャッジは「その証拠資料の信憑性を疑わしいものとして判定の際に考慮する」とし、その資料が支えている論点の評価に反映させる書き方をしている。

**確定**: 独立した軸を持たせず、**各内部要素（Present Situation / Effect / Impact）の評価要素として織り込む**。

- §1.5-C の条件ベース初期評価において、「出典が示されているか」「出典の種類は何か」「3.2.1 の必須項目が読み上げられたか」を各要素のチェックリスト項目として持つ
- 資料への攻撃（射程の指摘など）は、その資料が支えている要素の値を動かし、結果として Probability または Impact に効く

**副次的な利点**: demo では、ある資料が複数の観点を支えている場合にどの観点を削るのかが曖昧だった。資料を各要素に従属させれば、**攻撃は「どの要素の証明を崩したか」で一意に決まる。**

## 2. 取り込み候補（設計レベル）

### A. 判定モデル

**構造**（§1.5-D〜H の確定を反映）:

```
攻防イベント → 内部要素（Present Situation / Effect / Impact）の値を動かす
Probability = min(Present Situation, Effect)
論点の Strength = Probability × Impact
総括の比較 → 論点単位の重み（1.5 / 1.0 / 0.5）
側の合計 = Σ(Strength × 重み)
判定 = 両側の合計を比較。等しければ否定側（推定）
```

**demo から引き継ぐ原則**（v19 §2.3、集計式の変更後も有効）:
- **重みは常に正**（1.5 / 1.0 / 0.5）。したがって重みは論点の優劣を反転させない。総括が動かすのは効き具合だけ
- **総括に独立得点を持たせない**
- 重みは**総括の発言だけ**から決め、攻防の結果からは決めない（v20 §3.3 の役割分離。攻防の値＝論点がどれだけ残っているか、重み＝総括でどの土俵に比較を載せたか。三重評価ではない）
- 総括比較は⑫と判定の間の**独立ステージ**として扱う
- 片側の総括だけで比較の決着を付けない（後に述べる側が不利になるため）

**流用できる実装**: `state()`/`hist`（要素ごとの推移記録）、`holdSens()`/`comboGrid()`（感度分析の骨格）、`judge()` の側ごと集計の形。**流用しないもの**: `calc()` の `d_k` による差分計算と和の集約。

### B. 攻撃到達点・防御回復幅の体系

**立論10点尺度を除いた RUBRIC**（§1.5-C）。

- **攻撃の到達点**（攻撃の種類で決まり、攻撃前の値に依らない）: 出発点の喪失→2 / 前提の未提示→3 / 数値の側の崩壊→4 / 射程の指摘→−2
- **防御の回復幅**: 全回復→攻撃前の値へ / 部分回復→+2 / 言い直し→±0 / 落とし→−2 / **新規アタックとして無視→回復なし（§1.5-B-4）**
- 回復は攻撃前の値を上限、落としは応答機会が閉じた時点の値から引く

**規定のアタック類型との対応**: 2.1.3／2.1.4 はアタックを (A) not necessary / not unique、(B) no effect、(C) not important の三つで示す。**これは内部要素と一対一に対応する**（not necessary が Present Situation、no effect が Effect、not important が Impact への攻撃）。demo の4分類は**どこまで崩したか**を表すので、両者は直交する。つまり攻撃の記録は「どの要素に」（規定の三類型）×「どこまで」（demo の4分類）の組になる。

**Probability への波及**: Present Situation または Effect への攻撃が成立すると、min の結果として Probability が下がる。§1.5-E のとおり、どちらの環が効いているかは記録に残す。

**関連規定の補足**:
- 2.1.3 は否定アタックでの新規 Disadvantage を禁じる。「プラン実行に莫大なコストがかかる」は実質 Disadvantage なので禁止だが、「コストをまかないきれず解決性が落ちる」はアタックとして許される。価値だけを転倒する Value turn も許される
- 2.1.4 は肯定アタックでの否定アタックへの再反論を禁じる（ディフェンスで行う）。例外として、否定立論にアタックが含まれていた場合はそこへの反論が許される
- 2.1.2.2 は否定立論での肯定 Advantage への攻撃を、時間が余った場合に限って許す

### C. 保留（hold）・感度分析・人の確定

**規定上の根拠**: 4.1.4（2024年新設）は、ジャッジが引用証拠の英文および原文の開示を求めて確認できること、**この確認は全スピーチ終了後・その試合の判定の前に行うもの**と定める。立論が 600 語以内（2.1.10）かの確認も同様。**demo の保留設計はこの規定そのものである。** ただし同条は、発音が不明瞭で聴き取れなかった点を読みとるための確認は禁じている（聴き取れなかった議論は「内容の不明瞭な議論」として扱う）。この区別は analyzer の確認フローにも引き継ぐ。

- 保留の二段階: `provisional`（暫定）→ `hold`（保留・要確認）。付く時期を区別
- 保留は要素ごとに複数持て、短い種別 `t` と代替値候補 `alts` を持つ
- **単独感度**: 暫定値を動かして結果を再計算し逆転境界を求める。**積モデルでは感度の出方が和より鋭くなる**（Probability 側の変動が Impact 倍で効く）。単独感度の文には**固定条件**を必ず付け、データから生成する
- **組合せ感度表**: 保留2件を同時に動かした全組合せ。3件以上でも動く総当たり設計。**手打ちの数値は置かない**
- **同点セルの扱いは §1.5-A により「否定側（推定）」と表示する**
- **確認状態 `verify`**: 保留とは別の概念。「人が確認しても値が変わらない未確認」。未確認の二種類を区別して出す
- 採点の揺れ: `runs` と `threshold`。実測値でない場合は「デモ用の値（未実測）」と明記する
- **§1.5-G-3 により、論点数の上限判定も保留の対象**

**3.1.3 の関連規定**: 原文を見せられない場合、ジャッジはその証拠資料の信憑性を疑わしいものとして判定の際に考慮する。3.2.3 は相手チームによる証拠取り調べ（準備時間中の閲覧）を認める。demo の「資料同一性」保留は、この照合手続きが試合中に行われなかった場合の記録にあたる。

### D. 記録イベント構造の要素

- **hist（要素ごとの推移）**: 立論の値から始まり、動くたびに {値, 時刻, 種別, 適用規則} を積む。**§1.5-C により初期値と独立した攻防イベント列の原型。§1.5-E により min で捨てた側の値もここに残る**
- **rule フィールド**: 各 hits に段階表のどの規則を適用したかを付ける
- **cite（提示資料）**: 報告書名・発行機関・年・参照箇所・引用文言・読み上げた選手・未照合フラグを発言本体と分離して構造化。規定 3.2.1 が引用時に口頭で述べるべき事項（統計なら出典と年度、専門家なら氏名と肩書、報道なら社名と日付）を定めているので、**cite の必須項目はこの規定に合わせる**。§1.5-H により、cite はそれが支える要素に紐づく
- **ref（参考枠）**: 準備時間の相談は採点根拠にしない。参考として本文と分けて出す
- **質疑の「引き出し→回収」照合**: 質疑で引き出した材料が後のスピーチで実際に使われたかをセットで評価する。規定 2.1.9 は質疑を「不明点の確認」と「議論や証拠の検証」と定める
- **violation（手続き違反）**: 総括での新規デメリットを初出判定で検出し、算入しないが記録からは削除しない。**4.2.2 は「新しい議論」かの判断を相手チームの抗議の有無に左右されずジャッジが行うと明記**しており、エンジンが自動検出する設計はこれに沿う

### E. 説明生成の原則（v20 で確立。判定根拠テキストの要件仕様として移植）

1. **発言にない情報を解説で補わない**
2. **時系列違反の禁止**: まだ起きていない出来事を採点根拠に書かない（v20 §3.5 訂正の教訓）
3. **数値は全て計算結果から生成し、手打ちしない**
4. **側の名指し**: 「優位側」ではなく「優位の否定」
5. **素の値→重み反映後の併記**: 結論と両合計は必ず読める位置に
6. 解説の4区分構造化: 判断 / 根拠 / 点数の変更 / 未確認事項
7. 重みの妥当性は計算式だけでは証明できないことを明記し、根拠発言を時刻で示す
8. 土俵外の論点も、なぜ土俵外なのかを発言に基づいて書く
9. **【v04 追加】どの環が Probability を決めているかを明示する**（§1.5-E）。積モデルでは「Probability が低いので Strength が伸びない」という説明が頻出するため、その原因が Present Situation 側か Effect 側かを毎回示す
10. **【v04 追加】どちらの軸で比較が争われたかを記録から出す**（§1.5-F）。計算上は論点単位に畳まれるが、説明では軸を名指しする

### F. HEnDA プランルールの整理（規定 2.1.1.1 / 2.1.1.2 / 2.1.2）

- 肯定側は事前公開の論題定義が許容する範囲でプランを提示できる。自由に対象を狭めてよいわけではない
- プランが立論にない場合、論題定義に定められた一般的な立場を支持するとジャッジは解釈する（2.1.1.1）
- 範囲外プランから生じるメリットは判定で無視（2.1.1.2）
- 否定側が従うのは論題定義。ただしデメリットは**実際に提示されたプラン**から生じることの証明が必要 → プラン対象外だけを扱う資料への攻撃は「論題適合性」ではなく Effect への通常攻撃として追跡
- プランは立論後固定（2.1.1.1）。後続発言との矛盾照合の対象
- 対象限定による規模の評価は、論題適合性と分けて各要素の採点に織り込む
- **Advantage / Disadvantage は各最大2つ**。実質的に2つを超える言及があった場合、主要な二つ以外を無視する（4.2.1）。§1.5-G-3 のとおり保留の対象
- 各 Advantage / Disadvantage は三論点で証明することが求められる（§1.5-D の内部構造の根拠）

## 2.5 規定上の追加論点

- **3.2.1.1 独自計算値の規制（2025年新設）**: 原典に記載のない数値を独自計算で提示する場合、「自分で計算した」と明示し、計算に用いた全統計データを 3.2.1 の形で引用し、計算方法も述べなければならない。省略した場合、ジャッジは数値の信憑性を疑わしいものとして考慮する。**attack_type に対応パターンが要るか要検討**
- **2.1.10 立論600語制限（2024年改定）**: 平均 1分150語を超えてはならず、立論は最大600語。超過部分は無視して判定を出すことができ、コミュニケーション点の減点対象にもなる。**逐語反訳を持つ analyzer は語数カウントを自動化できる**。judge-support としての実用価値が高い
- **4.3 コミュニケーション点**: 5点満点・平均3の整数評価。判定（勝敗）とは別軸。analyzer の判定スコープ外だが ballot には存在する項目

**【要判断⑥】資料の働きの判定を誰が行うか**。§1.5-B の関門は「その資料が自陣の再構築に向いているか、相手への新規アタックか」の判定を要する。自動判定できるのか、保留として人に回すのか、両方か。判定を誤ると回復幅が丸ごと変わるので、感度分析の対象にすべき性質の判断でもある。

**【新規・要検討】値域と尺度の整合**。積モデルでは Probability と Impact の値域の取り方が結果に直接効く。両方を 1〜10 で取るのか、Probability を 0〜1 の係数として扱うのか（後者なら「ゼロにもなり得る」がそのまま表現できる）。§1.5-C の条件ベース初期評価を設計する際に、値域も併せて決める必要がある。要判断②に含めて扱う。

- **別の AI に実際に操作させる外部レビュー**を3巡回し、「計算が合う」と「判定理由に納得できる」は別問題であることを繰り返し確認した（v19 4.1c〜4.1e）。analyzer でも判定出力の受け入れ試験として同じ手法が使える
- 仕様書に**確定済み判断の章**（v20 §8）と**次版持ち越しの章**（§9）を置き、実装中の蒸し返しと横道を構造的に防いだ
- 受け入れ基準に**検算表**を置き、「コードを読んだだけの報告は不可、画面の実値で報告」を課した
- **規定の原文確認は取り込み前に行う。** §1.5-A〜C は、いずれも demo をそのまま移していれば analyzer に持ち込まれていた誤りである。確定済みの印は、規定との照合を省略してよい理由にはならない
- **demo の試行錯誤が規定に還元できる場面がある。** 5観点タクソノミは内部要素の細分であり、保留設計は 4.1.4 の手続きそのものだった。逆に、規定に翻訳できない部分（10点尺度への集約、和による集計）は demo 固有の制約の産物であり、移す必要がない
- **【v04 の教訓】立論の構成要素と判定軸は別物である。** v03 で両者を混同したのは、demo が5観点を横並びの評価軸として扱っていたことに引きずられたためである。demo は HTML 1枚で見せる制約から一次元の和に集約せざるを得ず、その形が「判定軸とはこういうもの」という誤った印象を与えた。**公式 Judge Sheet という一次資料に当たれば防げた誤りであり、規定確認を「ルールブックの条文」だけで済ませず、判定用紙そのものも確認対象に含めるべきだった。**
