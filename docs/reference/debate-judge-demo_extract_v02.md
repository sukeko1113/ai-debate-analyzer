## 1.5 規定確認で確定した3件【本版の中核】

v01 の時点では未確認だった論点を、大会ルールに当たって確定した。**いずれも demo の実装をそのまま移すと誤りになる箇所である。**

### A. 同点の扱い — 「判定不能」から「推定により否定側」へ

**demo の実装（誤り）**: v20 §8 ① で「同点の場合、エンジンは判定を出さない。人が確認して確定する」と確定していた。

**規定**: 4.2 は引き分けを認めていない。拮抗して見えても安易に同等とみなすことは許されず、細かい差を検証してどちらかに勝ちを付けよと命じたうえで、どうしても優劣がつけられない例外的な場合は**推定（presumption）に基づき否定側の勝利**とする。複数ジャッジの場合も各自が必ずどちらかに投票し、引き分けはないと明記されている。

**確定**:
- 最終差が 0 のとき、**判定は否定側とする（規定 4.2 の推定による）**
- 判定根拠を「推定による」と明示し、人の確認を要する印を付ける
- demo の設計意図（機械が勝手に確定させない）は救われる。意図は「判定を出さない」ことではなく「人が検証して確定する」ことだった
- **この推定は最終判定にのみ働く。** 個々の観点の `d_k` が 0 でも否定側に倒さない。それは「その観点では差がつかなかった」という事実であり、混同すると判定が歪む
- 実装: `judge()` の `wsum>0?'肯定側':wsum<0?'否定側':'引き分け'` を、0 を明示分岐させて `margin:0` ＋ 推定フラグを持つ状態にする

judge-support としてはむしろ価値の高い出力になる。人間ジャッジが最も迷う場面を名指しして渡すことになるため。

### B. ディフェンス・総括での資料の扱い — 関門の前置

**demo の実装（不十分）**: v20 §9 で「ディフェンスでの資料の扱いの規定確認」を次版に持ち越し、暫定的に「新しい議論は禁止、既存議論の資料による補強は可」という立場を採っていた。3:38 の解説もこの立場で書かれている。

**規定**: 4.2.2 は「新しい議論」として無視する対象に、**総括やディフェンスで相手チームの Advantage・Disadvantage の証明に対して新しいアタックの証拠資料が出た場合**を含めている。一方 2.1.5／2.1.6 はディフェンスの役割を「相手のアタックが無効であることを論じ、自陣の議論を再構築（reprove）すること」と定める。2.1.7／2.1.8 は総括での新しいアタックを禁じつつ、細かい証拠比較や大きな視点からの比較は許す。4.2.2 も「双方の議論をより深い角度から比較するような言及や証拠資料」は無視してはならないと明記。

**読み取れる線引き**: 禁じられているのは**資料の新しさ**ではなく、**その資料が相手への新規アタックとして働くこと**。自陣の議論を守り直すための資料提示は 2.1.5 の「再構築」そのもので、当然に許される。demo の書き方はこの区別を持たず、「全回復＝攻撃の核心に資料を伴って応答」という定義は、そのままでは規定違反の行為に最高評点を与えうる状態だった。

**確定**:
1. **回復幅の判定の前に「資料の働き」の関門を置く。** ディフェンスで資料が使われたとき、まずその働きを判定する。自陣の議論の再構築に向いていれば有効な防御として回復幅の判定に進み、相手の証明を新たに突くものなら 4.2.2 により無視して回復を与えない
2. 判定基準は**その資料が反論している対象**で切る。相手のアタックが突いた自陣の弱点を埋める資料なら再構築、相手の立論の証明を直接崩しにいく資料なら新規アタック
3. **「全回復」の定義から資料要件を外す。** 現行「攻撃の核心に、資料を伴って応答した」→「攻撃の核心に応答し、自陣の議論を再構築した。資料を用いる場合は、それが自陣の再構築に向けられていること」
4. **防御側の分類に「新規アタックとして無視」を追加する。** その部分は判定から除外され回復は生じない。到達点は攻撃後の値のまま。demo の attack 側には `violation` があったが防御側には無かった
5. **同じ適格性判定を総括の比較主張にも適用する。** ある観点で総括の比較を制したと判定する前に、根拠となった発言が比較として適格かを確かめる。不適格なら `c_k` は 0 のまま、重みは動かさない。demo は 4:20 の新規デメリットを violation として検出していたが、比較主張そのものの適格性は判定していなかった（**demo に無い要素。analyzer で新規に設計する**）

なお demo が v20 §3.7 で 3:14 の台詞を「読み返す時間がない」に変えた判断は、結果として規定に沿っていた。立論資料を引き直して自陣の調査範囲を示すのは再構築であり、規定上まったく問題ない。

### C. RUBRIC の尺度重なり — 「解消」でも「持ち越し」でもなく「移さない」

**demo の既知欠陥（v20 §9）**: ①尺度 8/7・7/6・6/5 の条件が排他でない（v20 は 9/8 のみ排他化）。②尺度 4・3・2 が攻撃到達点（数値の側の崩壊→4／前提の未提示→3／出発点の喪失→2）と二重定義。`scaleNote` の断り書き（「攻防後の値は段階表の加減で決まり、尺度の記述に再照合はしない」）で計算上の破綻は回避しているが、記述と値が食い違う例が既に出ている（3:20 の部分回復で到達する 5 は尺度5の記述と無関係）。

**原因の診断**: 書き方が雑だったのではなく、**10点尺度という一本の道具に性質の違う二つの仕事をさせている**ために生じている。立論の初期評価は「提出された議論がどれだけ支えられているか」の絶対評価。攻防後の値は「攻撃で何が失われ防御で何が戻ったか」の相対的な移動。同じ 1〜10 の目盛りに載せれば記述の衝突は必然。demo が断り書きで逃げたのは賢明だが根治ではない。

**analyzer では同じ設計にする必要がない**。demo は HTML 1枚で判定まで見せる制約があったため点数を一本の尺度に集約せざるを得なかったが、analyzer は構造化記録から判定を導出するのが中核で、記録が正確なら何を計算するかは後から決められる。

**確定**:
- **demo からは攻撃到達点と防御回復幅の体系だけを移す**（§1.5-B の修正を織り込んだ形で）
- **立論の10点尺度は移さない。** analyzer 側で**条件ベースの初期評価**として設計する。「出典があるか」「数字と価値づけの両方が支えられているか」「対象範囲との対応が述べられているか」等の**充足条件のチェックリスト**として持ち、点数はそこから導出する。どの条件が満たされ、どれが欠けているかが記録に残るので採点の再現性が上がる（analyzer の設計思想そのもの）
- **攻防による移動は初期値と独立したイベント列**として記録する。demo の `hist` が既にこの形。各イベントは攻撃類型・防御類型を持ち、到達点や回復幅はそこから計算される。尺度の記述とは照合しない。demo の `attackNote` が断り書きで言っていたことを、構造として実現する
- これにより尺度4・3・2 の記述は不要になり二重定義は解消。8/7・7/6・6/5 の重なりも条件チェックリスト化の過程で自然に解ける。**重なり問題は「持ち越す」のではなく「移さないことで発生させない」**
- この設計作業は §9.11 のラウンドで行う。取り込み自体はブロックしない

## 2. 取り込み候補（設計レベル）

### A. 判定モデル: 総括＝観点ごとの比較の勝敗＝重み

v19 §2 の核。analyzer の learnings に既に記録済みの原則（総括に独立得点を与えない）の**動く実装と検算**がここにある。

- 観点 k について `d_k`（肯定スコア − 否定スコア）、`c_k`（総括で制した側 +1/−1/0）、`w_k`（重み）
- 重み: 優位側が制した→1.5 / 劣位側が制し返した→0.5 / 決着なし・土俵外→1.0
- 最終差 = Σ(d_k × w_k)
- **不変条件3つ**（v19 §2.3）: ①符号は反転しない（w は常に正）②総括は個々の観点の勝敗を覆さない（重みの積み上げで最終判定の向きが変わるのは想定内）③総括に独立得点を持たせない
- 重みは**総括の発言だけ**から決め、攻防の結果からは決めない（v20 §3.3 の役割分離。攻防の点数＝論点がどれだけ残っているか、重み＝総括でどの土俵に比較を載せたか。三重評価ではない）
- 総括比較は⑫と判定の間の**独立ステージ**として扱う（判定の場面で根拠が見えるように）
- 片側の総括だけで比較の決着を付けない（後に述べる側が不利になるため、両者が出そろってから観点ごとに判定）
- **§1.5-B-5 の適格性判定を前置する。** 比較主張が規定上の正当な比較（2.1.7／2.1.8、4.2.2）でなければ `c_k` は 0
- **§1.5-A により、最終差 0 は「否定側（推定）」であって引き分けではない**

実装: `cmpW`（L1053–1056）と `calc`（L1058–1065）。フレームワーク非依存の純関数で、Zod 型を付ければそのまま導出判定層に置ける。

### B. 攻撃到達点・防御回復幅の体系

**立論10点尺度を除いた RUBRIC**（§1.5-C）。

- **攻撃の到達点**（攻撃の種類で決まり、攻撃前の値に依らない）: 出発点の喪失→2 / 前提の未提示→3 / 数値の側の崩壊→4 / 射程の指摘→−2
- **防御の回復幅**: 全回復→攻撃前の値へ / 部分回復→+2 / 言い直し→±0 / 落とし→−2 / **新規アタックとして無視→回復なし（§1.5-B-4、新設）**
- 回復は攻撃前の値を上限、落としは応答機会が閉じた時点の値から引く
- 全回復の定義は §1.5-B-3 のとおり再構築要件に置き換える

**規定側のアタック類型との対応**: 2.1.3／2.1.4 はアタックを (A) not necessary / not unique、(B) no effect、(C) not important の三つで示す。demo の4分類（出発点の喪失・前提の未提示・数値の側の崩壊・射程の指摘）はこれと**直交する切り口**である（規定は「何を攻撃したか」、demo は「どこまで崩したか」）。どちらが優れているという話ではなく、規定の三類型を経由すると analyzer の `attack_type` 体系と対応づけやすい（要判断②）。

**関連規定の補足**:
- 2.1.3 は否定アタックでの新規 Disadvantage を禁じる。「プラン実行に莫大なコストがかかる」は実質 Disadvantage なので禁止だが、「コストをまかないきれず解決性が落ちる」はアタックとして許される。価値だけを転倒する Value turn も許される
- 2.1.4 は肯定アタックでの否定アタックへの再反論を禁じる（ディフェンスで行う）。例外として、否定立論にアタックが含まれていた場合はそこへの反論が許される
- 2.1.2.2 は否定立論での肯定 Advantage への攻撃を、時間が余った場合に限って許す

### C. 保留（hold）・感度分析・人の確定

official judgment layer に直結する human-in-the-loop 設計。

**規定上の根拠（v01 になかった発見）**: 4.1.4（2024年新設）は、ジャッジが引用証拠の英文および原文の開示を求めて確認できること、**この確認は全スピーチ終了後・その試合の判定の前に行うもの**と定める。立論が 600 語以内（2.1.10）かの確認も同様。**demo の保留設計はこの規定そのものである。** 恣意的な工夫ではなく、規定に根拠を持つ手続きとして位置づけられる。ただし同条は、発音が不明瞭で聴き取れなかった点を読みとるための確認は禁じている（聴き取れなかった議論は「内容の不明瞭な議論」として扱う）。この区別は analyzer の確認フローにも引き継ぐ。

- 保留の二段階: `provisional`（暫定。条件しだいで人の確認に回る）→ `hold`（保留・要確認）。付く時期を区別（デモでは 2:42 で暫定、3:38 で保留に昇格）
- 保留は観点ごとに複数持て、短い種別 `t`（資料同一性／採点の揺れ）と代替値候補 `alts` を持つ
- **単独感度** `holdSens()`: 暫定値を動かして最終差を再計算し逆転境界を求める。値を動かすと差の符号で重みも変わるのでその分も含めて計算する。単独感度の文には**固定条件**（他方の保留を暫定値に固定した場合、という側名・値）を必ず付け、データから生成する
- **組合せ感度表** `comboGrid()`: 保留2件を同時に動かした全組合せの最終差。3件以上でも動く総当たり設計。セルは全て計算関数で再計算し、**手打ちの数値は置かない**
- **同点セルの扱いは §1.5-A により変更**。「同点」ではなく「否定側（推定）」と表示する
- **確認状態 `verify`**: 保留とは別の概念。「人が確認しても値が変わらない未確認」（例: 資料原文の読み方の正誤。点数は反論が提示された事実と種類の分類で決まっており原文確認で動かない設計）。未確認の二種類を区別して出す
- 採点の揺れ: `runs`（各回の値）と `threshold`（範囲がこの値以上で保留）。実測値でない場合は「デモ用の値（未実測）」と明記する

**3.1.3 の関連規定**: 原文を見せられない場合、ジャッジはその証拠資料の信憑性を疑わしいものとして判定の際に考慮する。3.2.3 は相手チームによる証拠取り調べ（準備時間中の閲覧）を認める。demo の「資料同一性」保留は、この照合手続きが試合中に行われなかった場合の記録にあたる。

### D. 記録イベント構造の要素

- **hist（観点ごとの推移）**: 立論の値から始まり、動くたびに {値, 時刻, 種別, 適用規則} を積む。**§1.5-C により、これが初期値と独立した攻防イベント列の原型になる**
- **rule フィールド**: 各 hits に段階表のどの規則を適用したかを付ける（採点の追跡可能性の要）
- **cite（提示資料）**: 報告書名・発行機関・年・参照箇所・引用文言・読み上げた選手・未照合フラグを発言本体と分離して構造化。規定 3.2.1 が引用時に口頭で述べるべき事項（統計なら出典と年度、専門家なら氏名と肩書、報道なら社名と日付）を定めているので、**cite の必須項目はこの規定に合わせる**
- **ref（参考枠）**: 準備時間の相談は採点根拠にしない。参考として本文と分けて出す（規定上も妥当。§3 参照）
- **質疑の「引き出し→回収」照合**: 質疑で引き出した材料が後のスピーチで実際に使われたかをセットで評価する。規定 2.1.9 は質疑を「不明点の確認」と「議論や証拠の検証」と定め、アタック後の質疑（⑥⑧）は原則としてアタックについて問うとする
- **violation（手続き違反）**: 総括での新規デメリットを初出判定で検出し、算入しないが記録からは削除しない（学習上、どの発言が算入されなかったか本人が確認できることが重要）。**4.2.2 は「新しい議論」かの判断を相手チームの抗議の有無に左右されずジャッジが行うと明記**しており、エンジンが自動検出する設計はこれに沿う

### E. 説明生成の原則（v20 で確立。判定根拠テキストの要件仕様として移植）

1. **発言にない情報を解説で補わない**（質疑の情報を立論の解説に先取りしない、出典の存在を解説側で補わない）
2. **時系列違反の禁止**: まだ起きていない出来事を採点根拠に書かない（v20 §3.5 訂正の教訓。攻撃時点の分類と、後の無応答による減点は別イベント）
3. **数値は全て計算結果から生成し、手打ちしない**（固定条件の側名・値、組合せ表のセル、仮定例まで）
4. **側の名指し**: 「+2」ではなく「肯定+2」。「優位側」ではなく「優位の否定」
5. **素点→重み反映後の併記**: 結論と両合計は表が見切れても必ず読める位置に
6. 解説の4区分構造化: 判断 / 根拠 / 点数の変更 / 未確認事項（データは `judg` / `basis` / `change` / `open` フィールド）
7. 重みの妥当性は計算式だけでは証明できないことを明記し、根拠発言を時刻で示す
8. 土俵外の観点も、なぜ土俵外なのかを発言に基づいて書く（攻撃では争ったが総括で軸にならなかった、の区別）

### F. HEnDA プランルールの整理（規定 2.1.1.1 / 2.1.1.2 / 2.1.2）

v19 4.1f で規定確認を経て確定した整理。規定原文と照合済み。

- 肯定側は事前公開の論題定義が許容する範囲でプランを提示できる。自由に対象を狭めてよいわけではない（範囲内かを決めるのは論題定義）
- プランが立論にない場合、論題定義に定められた一般的な立場を支持するとジャッジは解釈する（2.1.1.1）
- 範囲外プランから生じるメリットは判定で無視（2.1.1.2）
- 否定側が従うのは論題定義。ただしデメリットは**実際に提示されたプラン**から生じることの証明が必要 → プラン対象外だけを扱う資料への攻撃は「論題適合性」ではなく発生可能性・資料の関連性への通常攻撃として追跡
- プランは立論後固定（2.1.1.1）。後続発言との矛盾照合の対象
- 対象限定による規模の評価は、論題適合性と分けて各観点の採点に織り込む
- **Advantage / Disadvantage は各最大2つ**（2.1.1.3／2.1.2.1）。実質的に2つを超える言及があった場合、ジャッジは主要な二つ以外を無視する（4.2.1）。**analyzer は論点数の上限判定を持つ必要がある**
- 各 Advantage は (A) 現状が望ましくない (B) プランの効果 (C) 重要性 の三論点、各 Disadvantage は (A) プランがない状態が望ましい (B) プランの効果で発生 (C) 重要性 の三論点で証明することが求められる

## 2.5 v01 になかった規定上の論点

- **3.2.1.1 独自計算値の規制（2025年新設）**: 原典に直接記載されていない数値を独自の計算で算出して提示する場合、「自分で計算した」と明示し、計算に用いた全統計データを 3.2.1 の形で引用し、計算方法も明確に述べなければならない。省略した場合、ジャッジは数値の信憑性を疑わしいものとして考慮する。エビデンスと偽った場合は 3.1.2 の反則になりうる。**attack_type に対応パターンが要るか要検討**（新しい条項なので既存パターン体系に無い可能性が高い）
- **2.1.10 立論600語制限（2024年改定）**: 平均 1分150語を超えてはならず、立論は最大600語。超過部分は無視して判定を出すことができ、コミュニケーション点の減点対象にもなる。**逐語反訳を持つ analyzer は語数カウントを自動化できる**。judge-support としての実用価値が高い
- **4.3 コミュニケーション点**: 5点満点・平均3の整数評価。判定（勝敗）とは別軸。証拠資料の閲覧に協力しない場合等の減点規定（4.3.1）もある。analyzer の判定スコープ外だが、ballot には存在する項目

## 3. 移さないもの

- UI 全般（SVG 人物、机、吹き出し、右列レイアウト）、Web Speech API の音声合成と文分割、効果音
- シナリオデータの中身（架空試合の台詞・点数値）。**構造だけ**を持ち込む
- HTML 1枚構成という制約そのもの
- **立論の10点尺度**（§1.5-C）

**準備時間の扱いについて**: demo は準備時間の相談台詞を採点に用いない（参考表示のみ）としている。規定 2.2.5 は、試合中（準備時間含む）に助言を行えるのは出場メンバーのみと定め、補欠や観客席からの助言・資料提供は原則不戦敗とする。2.2.6 は両チームとも準備時間中の打ち合わせができるとする。いずれも発言内容を判定材料とする規定ではないので、demo の扱いは妥当。

## 4. ai-debate-analyzer v10 へのマッピングと【要判断】

| demo 側 | analyzer 側の受け皿 | 備考 |
|---|---|---|
| SUMCMP（arena/c/重み） | `comparison_events`（8比較軸、Defense ステージ跨ぎ） | 比較の**適格性判定**（§1.5-B-5）を前置する層が新たに要る |
| 攻撃到達点・防御回復幅 | §9.11 パターン体系（attack_type 9値 + binding 80パターン） | パターン→到達点クラスの対応表が必要（要判断②） |
| 立論10点尺度 | **移さない。** 条件ベースの初期評価として新規設計 | §9.11 のラウンドで扱う（要判断②に統合） |
| hold / verify / 感度 | official judgment layer、ballot・assessments 分割の未決事項 | 規定 4.1.4 が根拠。Phase A/B 配置の判断と連動（要判断③） |
| 説明生成の原則 E | 判定根拠テキスト生成の要件 | §17/18 系か付録に要件として固定 |
| プランルール F | 規定照合ロジック | 2.1.1.x/2.1.2 は確認済み。論点数上限（最大2）の判定も追加 |

**【要判断①】観点タクソノミの対応**。demo の5観点（現状との連続性・発生可能性・インパクト・解決性/不可避性・資料の裏づけ）はデモ固有。analyzer の判定は公式ジャッジシートの Probability / Value / Strength にスコープし、`occurrence_likelihood` へのリネームで公式列との衝突も回避済み。重み付けメカニズム（§2-A）は移せるが、**重みを掛ける軸を何にするか**（公式3指標か、内部分析層の次元か、comparison_events の8軸か）は設計判断。規定 2.1.1.3／2.1.2.1 の三論点（現状・効果・重要性）が規定側の自然な単位である点は判断材料になる。

**【要判断②】立論評価の条件設計と、攻防イベントとの接続**（v01 から性質が変わった）。§1.5-C の確定により、これは「80パターンに到達点クラスを付与する」だけでなく、**立論の初期評価を充足条件のチェックリストとして設計し、攻防イベント列と層を分ける**作業になる。§9.11 のラウンドで扱う。規定の三類型（not necessary / no effect / not important）を経由点にするかもここで決める。

**【要判断③】保留・感度の実装フェーズ**。ballot 一意制約と assessments 分割の Phase A/B 未決事項と同じ判断枠。保留はスキーマに乗る（hold の state/t/alts/runs/threshold、verify）ので、**スキーマファーストの規律どおり Ch.12（テーブル定義）と Ch.13（Zod）に先に入れてから**実装フェーズを決める。

**【要判断④】1対1比較からの一般化**。demo はメリット1本 vs デメリット1本の固定構成で `d_k` が単純な引き算で済んでいる。規定は各side最大2つを認めるので、実試合では「どの論点対どの論点の比較か」の対応付けが要る。comparison_events が論点対を持つ設計なら受け皿はあるはずだが、`d_k` の定義を論点対ごとに拡張する式の確定が必要。4.2.1（2つを超える言及があれば主要二つ以外を無視）の判定ロジックも併せて設計する。

**【要判断⑤】総括比較の独立ステージ化**。demo は⑫と判定の間に導出ステージ「総括比較」を置いた。analyzer の記録/表示にこの導出ステージ概念を入れるか（公式12ステージへの忠実性との整理）。

**【要判断⑥】資料の働きの判定を誰が行うか**（新設）。§1.5-B の関門は「その資料が自陣の再構築に向いているか、相手への新規アタックか」の判定を要する。これは自動判定できるのか、保留として人に回すのか、あるいは両方（自動判定＋確信度が低ければ保留）か。判定を誤ると回復幅が丸ごと変わるので、感度分析の対象にすべき性質の判断でもある。

- **規定の原文確認は取り込み前に行う。** 本版の §1.5 三件は、いずれも demo をそのまま移していれば analyzer に持ち込まれていた誤りである。特に同点の扱いは、demo が「確定済み判断」として明記していたものが規定と衝突していた。確定済みの印は、規定との照合を省略してよい理由にはならない
